## Essence

Lexing and parsing turn a flat string of characters into a tree that shows the program's structure. The lexer (scanner) groups characters into tokens such as identifiers, numbers, operators and keywords, discarding whitespace and comments. The parser groups tokens into an Abstract Syntax Tree (AST) according to a grammar, or reports where the input breaks the grammar. The split follows the [Chomsky hierarchy](../../02-theory-of-computation/02-automata-and-formal-languages/chomsky-hierarchy.md): tokens are regular languages, recognised in linear time by finite automata, while nesting (parentheses, blocks) needs a context-free grammar and a stack. The single idea is to **use the weakest machine that can do each job**, because weaker machines are faster, simpler and give stronger guarantees.

## Core tenets

1. **Lexing is regular, so it runs as a finite automaton.** Each token class is a regular expression (`[a-zA-Z_][a-zA-Z0-9_]*` for identifiers). Tools such as lex combine them, convert the result into a Deterministic Finite Automaton (DFA) via subset construction, and minimise it. The DFA reads each character once, giving linear-time scanning with a small table.
2. **Lexers resolve ambiguity by longest match, then by priority.** `ifx` is one identifier, not the keyword `if` followed by `x`, because the lexer takes the longest prefix that forms a token. When two rules match the same length (`if` as keyword or identifier), the earlier rule wins. This simple policy is why keywords are "reserved".
3. **Parsing needs a stack because nesting is unbounded.** Matching parentheses to arbitrary depth is not regular (pumping lemma), so no finite automaton can do it. Context-free grammars describe nesting, and the machines that recognise them are [pushdown automata](../../02-theory-of-computation/02-automata-and-formal-languages/context-free-grammars-and-pushdown-automata.md). General context-free parsing costs O(n³) (the Cocke–Younger–Kasami (CYK) and Earley algorithms), so practical languages are designed so a deterministic linear-time parser suffices.
4. **Top-down (LL) parsing predicts; recursive descent is its hand-written form.** An LL(k) parser reads Left to right, builds a Leftmost derivation, and chooses each rule by looking ahead k tokens. Recursive descent writes one function per non-terminal, which is easy to read, gives good error messages, and is what most production compilers (the GNU Compiler Collection (GCC), Clang, the Go and Rust compilers) actually use.

   ```python
   def expr():               # expr := term (('+'|'-') term)*
       node = term()
       while peek() in ('+', '-'):
           op = advance(); node = BinOp(op, node, term())
       return node
   ```

5. **Left recursion breaks top-down parsing; precedence climbing fixes expressions.** A rule `expr := expr '+' term` makes a recursive-descent parser call itself forever without consuming input. Grammars are rewritten into iteration as above, and operator precedence is handled by Pratt parsing or precedence climbing, which assign each operator a binding power.
6. **Bottom-up (LR) parsing defers decisions and accepts more grammars.** An LR parser shifts tokens onto a stack and reduces when the top of the stack matches a rule's right side, building a Rightmost derivation in reverse. Because it decides after seeing a whole phrase, LR(1) handles every deterministic context-free language (Knuth, 1965). Look-Ahead LR (LALR(1)) tables, generated by yacc and Bison, are the compact practical variant. Conflicts (shift/reduce, reduce/reduce) reveal ambiguities in the grammar.
7. **Error recovery is a design goal, not an afterthought.** A compiler should report many errors per run, not stop at the first. Parsers resynchronise by skipping to a known token (a semicolon, a closing brace) and continuing. Modern tools for editors go further, producing a tree even for broken input, because the code being edited is almost always temporarily invalid.
8. **The parse tree is discarded; the AST is kept.** A concrete parse tree records every grammar rule used, including those for precedence. The parser instead builds an AST that keeps only meaningful structure and records source positions for error messages. Everything downstream works on the AST.

## Key concepts

| Term | Meaning |
|---|---|
| Token | A classified lexeme: identifier, literal, keyword, operator |
| Lexer (scanner) | The phase that turns characters into tokens, usually a DFA |
| Deterministic Finite Automaton (DFA) | A finite state machine with one transition per state and symbol |
| Context-free grammar | Rules `A → α` that rewrite a non-terminal regardless of context |
| LL(k) | Top-down parsing, left to right, leftmost derivation, k tokens of lookahead |
| LR(k) | Bottom-up parsing, left to right, rightmost derivation in reverse, k tokens of lookahead |
| Shift/reduce conflict | An LR table entry where the parser cannot decide between shifting and reducing |
| Recursive descent | A hand-written top-down parser with one procedure per grammar rule |
| Abstract Syntax Tree (AST) | The structural tree produced for later phases |

## Common misconceptions

- **"Parsing is the hard part of a compiler."** It is the best-understood part, solved in the 1960s and 1970s; optimisation and code generation are where the open problems are.
- **"You can parse HyperText Markup Language (HTML) or nested code with a regular expression."** Pure regular expressions cannot match unbounded nesting; that needs at least a context-free parser.
- **"Real compilers use parser generators."** Many do not: hand-written recursive descent dominates in production because it is faster to debug and gives better diagnostics.
